## Claim 1 — Go concurrency bugs are pervasive, and they need a taxonomy

*(review claim C1; paper Table 5, Table 6)*

**Paper.** The first empirical study of Go concurrency bugs. 171 bugs in six
production-grade Go programs (Docker, Kubernetes, gRPC, CockroachDB, etcd,
BoltDB), labelled along two independent dimensions: *cause* (shared-memory
access vs. message passing) and *behaviour* (blocking vs. non-blocking).

**Ours (L1).** Re-parse the pinned upstream snapshot and recompute Tables 5, 6,
7, 9 and 10 from the paper's definitions, not from the paper's spreadsheet.

| | blocking | non-blocking | shared memory | message passing |
|---|---|---|---|---|
| Paper | 85 | 86 | 105 | 66 |
| Ours (169 commit-backed) | 83 | 86 | 105 | 65 |
| Delta | −2 | 0 | 0 | −1 |

**Deviation.** Two causes, both fully attributed:

1. The two excluded BoltDB rows (`boltdb#392`, `boltdb#240`) account for
   −2 blocking, −1 shared memory and −1 message passing. Including them makes
   the blocking count 85 again, matching the paper.
2. `kubernetes#11298` carries both a shared-memory and a message-passing label
   in the workbook. The paper assigns it one cause; we retain both labels.
   That is +1 shared memory for Kubernetes, and it is why our Table 6 totals
   84 cause assignments for 83 blocking bugs.

Net effect: shared memory is unchanged at 105 because the +1 and the −1
cancel; message passing is −1 because only the excluded BoltDB row is
message-passing. Full cell-by-cell account in `docs/discrepancy_analysis.md`.

**Verdict: supported.** The taxonomy reproduces. The four differing cells are
exactly the cells the two documented causes predict, and under the paper's own
assignment convention our recomputation matches Table 5 for all six
applications and Table 6 in all six cause columns. We did not reproduce the
paper's *scope* of 171 commits, because two of those rows carry no commit; the
taxonomy itself is confirmed.

**Status.** L1 done (A's statistical scope; the pinned-data pipeline was
implemented by C in commit `1b3e968`).

## Claim 2 — Most of these bugs are not classic shared-memory races, and their fixes vary with their causes

*(review claims C2 and C3; paper Table 9, Table 7, Table 10)*

**Paper.** More than half of the 171 bugs are not traditional shared-memory
races but problems specific to Go's own concurrency idioms — misuse of Go
libraries, goroutine and channel misuse, and similar. The paper therefore
answers the long-running "message passing vs. shared memory" debate for Go:
message passing is *not* automatically safer. Separately, the paper finds a
high correlation between a bug's cause and the strategy used to fix it: bugs
whose cause involves a particular synchronisation primitive are usually fixed
by adjusting that same primitive.

**Ours (L1).** The non-traditional label is a *separate* classification from
the shared-memory / message-passing cause axis, and the two must not be
substituted for one another. Counting the workbook's own non-traditional label
(column L for blocking rows, column H for non-blocking rows):

| Behaviour | Rows in scope | Rows carrying a non-traditional label |
|---|---:|---:|
| blocking | 83 | 54 |
| non-blocking | 86 | 40 |
| **Total** | **169** | **94** |

**94 / 169 = 55.6 %** carry a non-traditional label.

Reproduce with the standard-library parser, no third-party packages:

```sh
python -c "import sys; sys.path.insert(0, 'scripts'); from parse_dataset import read_sheets, parse_bugs, DATASET_PATH; bugs=parse_bugs(read_sheets(DATASET_PATH)); print({kind:sum(b.flag('L' if kind=='blocking' else 'H') for b in bugs if b.behavior==kind) for kind in ('blocking','non-blocking')})"
```

For the fix strategies we reproduce the paper's own category definitions and
no reinterpretation:

- **Table 10** (non-blocking fix strategies) matches the paper in **all 35
  cells**, including the total row.
- **Table 7** (blocking fix strategies) matches in every cell **except three**,
  each traced to the data-scope causes above: Mutex/Misc 2 → 1, Wait/Remove
  1 → 2, ChanWith/Remove 4 → 3. Its Remove total of 21 is 21 *cause
  assignments* from 20 distinct records, because the doubly-labelled
  `kubernetes#11298` contributes to two cause rows.

**Verdict: supported for the counts, and deliberately not extended.** The
non-traditional majority reproduces at 55.6 %, and the cause-to-fix-strategy
correlation reproduces in Tables 7 and 10. Two boundaries are enforced. First,
55.6 % is a majority claim *within this dataset*: it is not a universal
failure probability for Go constructs, and it is not the same quantity as the
shared-memory share. The five CSV tables carry no dedicated traditional /
non-traditional column, so this count is a supplementary workbook-label count
whose source coordinates (blocking column L, non-blocking column H) travel
with the number wherever it is used.

Second, the fix-strategy tables do **not** establish that upstream fixes are
shallow, incomplete, or that they introduce new bugs. Counting small patches
or added synchronisation cannot show that developers failed to identify a root
cause, and the current work contains no experiment measuring those
properties. A before/after reproducer control can test whether a specific fix
removes our observed symptom; it cannot on its own prove a general claim
about fix quality. We therefore assert the correlation, and not the quality.

**Status.** L1 done for the strategy counts. The fix-quality question remains
open and is listed in the limitations.

## Claim 3 — Go's built-in detectors miss most of these bugs

*(review claim C4; paper Table 8, Table 12)*

**Paper.** The paper evaluates Go's built-in deadlock detector and race
detector against the bugs it re-ran:

- The **deadlock detector** fires on only **2 of 21** reproduced blocking bugs
  (paper Table 8). The paper ran each deterministic blocking bug once.
- The **race detector** fires on **10 of 20** reproduced non-blocking bugs
  within 100 runs each (paper Table 12) — **exactly half** of that sample.

**Ours (L2).** Same protocol: rebuild each selected bug at its buggy commit,
trigger it, and record whether the built-in detectors fire. The protocol needs
at least 3 runs per bug for statistics and 100 runs for the race-detector
experiment.

**Required discrepancy statement.** The commit-backed dataset inventory is
marked **19 blocking / 23 non-blocking** as reproduced, while the paper reports
**21 / 20**. Both excluded BoltDB issue-only rows are also marked reproduced,
so including them makes the workbook's blocking flag count 21. The non-blocking
workbook has 23 flagged rows, so that disagreement with the paper remains
unexplained. These flags describe upstream annotations, not this team's
completed runs. Our three week-two detector observations are separately
identified as extracted-model results in `repro/week2-results.md`.

**Verdict: inconclusive on our side.** The paper's detection gap is
established in the paper; our own coverage is **not yet measured**. The
candidate selection and the reproducer contract are complete, and the
experiment environment is built and measured (see `docs/environment.md`,
measured 2026-11-14 by `docker/verify.sh` in CI). Three extracted models have
passed 3/3 symptom trials and fixed controls in the pinned image
([`repro` CI run](https://github.com/Henry0630/CS340-Replication/actions/runs/43679686655)).
They are not whole-application rebuilds at the pre-fix revisions, so their
detector observations cannot estimate application-level coverage. We quote the
paper's detector numbers as the paper's and state that our comparable coverage
is unmeasured.
Quoting a coverage figure of our own before that happens would be an estimate
presented as a measurement.

**Status.** L2 — three extracted models measured, plus one application-level
blocking bug measured on a non-canonical host; the canonical whole-application
run is wired in `.github/workflows/repro.yml` (job `grpc-793-app`) but had not
executed when this section was written. Raw logs are artifacts of the linked
`repro` CI runs under `results/raw/<bug>/`; the observations and scope are
recorded in `repro/week2-results.md` and `repro/week3-results.md`.

**Week-three application-level observation (non-canonical host).** The complete
grpc-go revision for grpc-793 was built in GOPATH mode with Go 1.12.17 and run:
3/3 buggy trials ended in the Go runtime's `all goroutines are asleep -
deadlock!` report at `server.go`, and 3/3 fixed controls completed. The
extracted model re-run under the same Go 1.12.17 toolchain also reported the
deadlock in 3/3 trials, while the week-two Go 1.22.4 image recorded timeouts
without a runtime report (see `repro/week3-results.md`). For this bug the
detector outcome is therefore toolchain-sensitive, and the extracted model did
not change it when the toolchain was held constant. This is one application-
level observation, not a coverage estimate: the paper's 2/21 blocking-bug
detection remains the paper's figure.

## Extension — does Go 1.22 close the loop-variable bug class?

**Paper.** The paper's observation about anonymous-function bugs is about Go
as it was written in 2015–2018. The loop-variable semantics change is a
**later** language change (Go 1.22); it is not a claim made by the 2019 paper,
and it is not a result we may claim until we have run it.

**Ours (planned).** The only factor we change is the Go language version: the
same image, `golang:1.21.13-bookworm` vs `golang:1.22.4-bookworm`. Go 1.22
gave each loop iteration its own variables.

**Controls we must record, or the comparison proves nothing:**

- the module's `go` directive and the actual toolchain version, since the
  language version selected follows the directive;
- any compiler flags;
- the base-image and compiler differences, recorded rather than assumed.

Switching a container tag alone is **not** evidence that the intended language
semantics changed. The hypothesis we will test is narrow: the new loop-variable
semantics remove selected *loop-capture* symptoms; anonymous-function bugs
involving other shared state need not disappear. Source, input, dependencies
and every other setting are held fixed.

**Status.** Planned. B builds and pins the images, C runs the comparison. No
extension result is claimed in this report.

## Rule

A number may only appear in the report if it appears in this file, with a
pointer to where it was produced: `results/tables/*.csv` for L1,
`results/raw/<bug>/` CI artifacts for L2. Deviations are registered in `docs/discrepancy_analysis.md`, the report-facing account written by D; A owns the setup-level deviation log, which is `deviations.md` at the repository root on `a-dataset`.
Suggested wording and judgments from a review are kept distinct from new
measurements: a reviewer's suggestion is not evidence.
